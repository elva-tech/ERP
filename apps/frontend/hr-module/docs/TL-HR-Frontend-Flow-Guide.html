How permission tags work: The backend sends allowed permission keys to the frontend at login. The frontend compares each component’s permission key against this list. If the key exists, the component is displayed; if not, it is hidden. This comparison happens locally in React and does not call the backend for every component. Hiding UI is not security — backend APIs still enforce authorization (see Page 5).

Page 2 — Why catalog.js contains only HR permissions

Short answer: catalog.js is the menu of all possible actions in the HR app (like a master list). Manager and Employee are not separate lists in the frontend. The backend picks which items from that master list each person gets, based on membership.role (company_admin / hr_manager / employee).
TL nameStored in DB as roleWho builds their list?
HR ADMINcompany_adminBackend: almost all hr.* codes
HR (manager)hr_managerBackend: smaller list (TL doc v1.0)
EMPLOYEEemployeeBackend: self-service codes only

Same frontend code for everyone. Two users open the same React app. User A’s API response has 80 codes; User B has 15. Sidebar and buttons only check: “Is my code in my list?”

Page 5 — API connection and backend touchpoints

Three layers of HTTP from the UI

LayerFileResponsibility
HTTP helpersrc/api.jsShared fetch wrapper: sends cookies, parses JSON, surfaces 401 to the app. All services use this — modules should not duplicate raw fetch logic.
Feature servicessrc/services/*One function per domain action (e.g. list employees, create payroll run). Calls api.js with the right path and body.

The browser does not send the full permissionCodes array on every feature request. The session cookie identifies the user; the backend loads membership and permissions again (or equivalent checks) on each protected route.

How the files relate (not just a file list)

  • main.jsx boots the app and hands control to AuthGate.jsx, which is the only place that loads session + membership access from the backend.
  • api.js is the shared pipe to backend auth and data routes; AuthGate and all services/* depend on it.
  • App.jsx owns layout and routing: it consumes access from AuthGate, provides it to AccessProvider, asks navigation.js for a filtered menu, and passes that menu to shell.jsx.
  • catalog.js supplies stable HR.* strings to navigation.js, useModuleAccess.js, and permission wrappers; access.js implements the actual set membership checks used by AccessProvider.
  • routes.jsx is the full route registry; navigation.js intersects it with the user’s codes. Modules never talk to the sidebar directly.
  • useModuleAccess.js, Can.jsx, and PermissionOnly read the same context list; modules call services, and services call api.js again for real data.

Side-by-side

  <h1>Payroll Processing</h1>
</Can>

What happens on each render (8 steps)

  1. Frontend defines the permission key in catalog.js (e.g. HR.payroll.processing.view → "hr.payroll.processing.view").
  2. Backend decides whether this user’s role should receive that key (hrms-permission-catalog.js).
  3. At login, backend sends the allowed list in memberships[].access.permissionCodes.
  4. AccessProvider stores that list in React context.
  5. Can.jsx calls useAccess() (in the repo: hasPermission(permission) — see verified snippet in Appendix).
  6. Can checks whether the supplied key exists in the list.
  7. If yes → render children; if no → render fallback (default: nothing).
  8. Clicking a visible button still runs a separate API call, validated on the server.

Simplified examples (illustrative)

The real Can.jsx also supports anyOf / allOf and uses hasPermission, not canPerform, for the single-code case.

function Can({ permission, children }) {
  const { hasPermission } = useAccess();
  return hasPermission(permission) ? children : null;
}

function hasPermission(permissionCodes, code) {
  return new Set(permissionCodes).has(code);
}
Critical: The permission tag does not call the backend to verify each component. It compares its key against the list already received from /api/auth/me (or /api/access/context after a company switch).

Visibility vs action

<Can permission={HR.payroll.processing.view}>
  <button onClick={handleProcessPayroll}>Process Payroll</button>
</Can>

The tag only controls whether the button appears. handleProcessPayroll → payroll service → api.js → backend enforces the operation.

How the entire permission system works

The backend determines permissions from the user’s company membership role. At login, GET /api/auth/me returns an array of allowed permission strings. The frontend keeps its own catalog.js of keys used in components. AccessProvider stores the array from the server.

When JSX uses <Can permission={HR.payroll.processing.view}>, React checks whether that exact string is in the list. The same list drives navigation.js (sidebar) and App.jsx (route guard). On button click, a service calls the backend, which validates access again.

Remember these four pieces:
1. catalog.js — defines frontend permission keys.
2. hrms-permission-catalog.js — backend decides which keys each role gets.
3. AccessProvider + Can.jsx / PermissionOnly — compare keys and control UI visibility.
4. Backend APIs — enforce authorization on data and operations.

8.1 Real code — Can.jsx (generic only)

apps/frontend/hr-module/src/permissions/Can.jsx 
export function Can({ permission, anyOf, allOf, fallback = null, children }) {
  const access = useAccess();
  let allowed = true;
  if (permission) {
    allowed = access.hasPermission(permission);
  } else if (anyOf?.length) {
    allowed = access.hasAnyPermission(anyOf);
  } ...
  if (!allowed) return fallback;
  return children;
}

Notice: no HR. import. Parent supplies permission.

export function PermissionOnly({ permission, children, message }) {
  const access = useAccess();
  if (!access.canPerform(permission)) {
    return <Notice notice={{ type: "info", message: "You do not have permission..." }} />;
  }
  return children;
}

export function ManagerOnly({ permission = HR.payroll.processing.view, children, ... }) {
  return <PermissionOnly permission={permission}>{children}</PermissionOnly>;
